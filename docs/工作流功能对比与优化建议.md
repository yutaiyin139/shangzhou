# 熵舟 vs Dify —— 工作流功能实现详细对比与优化建议

> 生成日期：2026-09-21
> 对照基准：**本机运行的 Dify**（`http://localhost`，版本 1.17.1，含实时协作画布）+ 本地源码 `dify-1.17.1/`
> 分析对象：**熵舟智能体平台**（`http://localhost:5173`，前端 Vue3+VueFlow / 后端 Flask+MySQL）
> 数据来源：前端 `front/src/`、后端 `backend/`、数据库 `szagent`（MySQL root/0000）、Dify 运行时界面探查、Dify 1.17.1 源码静态分析、以及**对熵舟工作流引擎的在线实测**
> 重点：工作流应用功能实现，尤其是**画布**与**节点编辑**；核心实现**严格对比 Dify**

---

## 〇、执行摘要（TL;DR）

| 维度 | 熵舟现状 | Dify 1.17.1 | 差距量级 |
|------|----------|-------------|----------|
| 节点类型数量 | 前端注册 **27**、引擎可执行 **25** | 引擎 **30**、前端 **32**（含循环体/触发器等） | 基本持平，个别缺项 |
| 画布交互深度 | 基础（拖拽/连线/小地图/自动布局/撤销重做） | 完整（框选/复制粘贴/右键菜单/连线插入/辅助线/注释/协作/变量检查/检查清单） | **差距大** |
| 节点编辑面板 | 原生表单简化版 | 富交互（变量树选择器/上下文/记忆/视觉/结构化输出/失败重试/异常处理） | **差距大** |
| 变量体系 | 扁平 context（无 node 命名空间） | 结构化 `variable_selector`（node 命名空间 + 类型） | **架构性差距** |
| 分支路由 | **实测失效（P0，见第六章）** | 迭代式动态图执行，正确 | **P0 正确性缺陷** |
| 运行调试 | 有断点单步调试（**强于 Dify**） | 有运行/追踪/上次运行，无断点 | 熵舟局部领先 |
| 草稿自动保存 | 手动保存 | 自动保存草稿 + 发布 diff | 中等 |
| 实时协作 | 无 | 有（多人光标/在线用户） | 高（可选） |

**一句话结论**：熵舟在"广度"上（节点数量、MCP/子工作流/批量任务/触发器等）已快速追平甚至在个别点上超越 Dify；但在"**深度**"上——尤其是**画布交互**、**节点编辑面板的富交互**、**变量体系的正确性与健壮性**、以及**分支路由引擎的正确性**——与 Dify 仍有明显差距，且存在 **1 个已被实测证实的 P0 正确性缺陷（条件分支路由失效）**，应最优先修复。

## 一、整体架构对比

### 1.1 技术栈

| 层 | 熵舟 | Dify 1.17.1 |
|----|------|-------------|
| 画布库 | `@vue-flow/core` (Vue 3) | `reactflow` (React/Next.js) |
| 自动布局 | `dagre` | `dagre` + 自定义 organize |
| 状态管理 | Pinia + 组件内局部状态（**双份，见 §5.4**） | zustand + jotai |
| 后端框架 | Flask（单体，端口 5000） | Flask(api) + Celery worker/beat + WebSocket 独立服务 |
| 运行时引擎 | `engine/workflow_runner.py`（自研 graphon 风格 NodeFactory） | 独立包 **graphon**（1.17 抽出） |
| 数据库 | MySQL `szagent`（单实例） | PostgreSQL（144 表）+ pgvector + Redis |
| 代码沙箱 | `utils/sandbox.py`（本地） | `sandbox` + `local_sandbox` 容器 |

架构范式两者"神似"（都是 NodeFactory/节点注册 + DAG 拓扑 + 阻塞/流式双通道），但 **Dify 的画布前端与运行时引擎的成熟度、以及变量/分支模型的正确性设计远高于熵舟**。

### 1.2 数据模型对比

- **熵舟**：兼容 Dify 的 `dify_*` 表族（`dify_apps` / `dify_workflows` / `dify_workflow_runs` / `dify_workflow_node_executions` …），并叠加自有表（`workflow_versions` / `workflow_comments` / `workflow_pauses` / `workflow_test_runs` / `workflow_debug_sessions` / `workflow_schedule_plans` 等，szagent 实测共 57 表）。graph 以 JSON 存于 `dify_workflows.graph`。
- **Dify**：144 表，draft/published 分离（`workflow_draft_variables` 等）、`workflow_app_logs`、`workflow_node_executions`、`message_annotations` 等更细粒度。

两者 graph JSON 结构高度兼容（node `data.type`、edge `sourceHandle` 等），熵舟可**导入 Dify DSL**，这是很好的互操作优势。但**兼容"结构"不代表兼容"语义"**——分支句柄命名不一致即为典型（见 §6.2）。

### 2.3 一个渲染架构问题（性能/一致性隐患）

`WfCanvas.vue` 用 `watch(() => props.graph, syncFromGraph, {immediate:true})` 在**每次 graph 变化时全量重建 `elements` 数组**（`[...nodes, ...edges]`），而内部拖拽/连线又 `pushGraphUpdate()` 反向 `emit('update:graph')` 回父组件，形成"**受控-回环**"。当大图（数百节点）时全量重建会带来明显卡顿，且 `markRaw` 仅包裹了组件而非 nodes 数组，VueFlow 内部仍会对每个节点做深层响应式代理。**优化见 §8.3**。

### 3.3 关键短板（节点编辑）

1. **无变量引用选择器（VarReferencePicker）**：Dify 编辑体验的护城河之一。熵舟所有涉及变量的地方都是纯文本框，用户既看不到"有哪些上游变量"，也无法点选插入，直接导致 LLM/条件/HTTP 节点**上手难度高、易写错**。
2. **富字段"后端已支持、前端未暴露"**：结构化输出、失败重试、异常处理在引擎层已有实现，但面板没做——**这是投入产出比最高的补齐点**（后端零改动，仅加前端表单）。
3. **IF/ELSE 与运行引擎的变量语义不一致**（详见 §6）：面板选的是"假变量列表"，运行引擎读的是 `case.conditions[].variable` 点号路径，二者脱节。

## 四、执行引擎与变量体系对比

### 4.1 熵舟引擎结构（graphon 风格，设计良好）

- `engine/node_factory.py`：`NodeFactory` 注册表，kebab/snake 双别名，新增节点只需 `nodes/xxx.py` + 一行 register —— **扩展性与 Dify 一致，值得肯定**。
- `engine/nodes/*.py`：20 个节点实现；`workflow_runner.py`：图遍历调度 + 阻塞 `run_workflow` + 流式 `run_workflow_stream`（LLM/Agent 有 token 级流式，Agent 推送思考链）。
- 支持：超时（默认 120s/节点）、重试（指数退避）、迭代子图识别、Human-in-the-loop 暂停/恢复（`__human_input_pause__`）、版本 diff。

### 4.2 变量体系：扁平 context vs node 命名空间（架构性差距）

**Dify**：每个节点输出以 `node_id` 为命名空间，引用用 `variable_selector: [node_id, 'text']`，运行时按路径解析，天然避免同名冲突、支持类型/树形。

**熵舟**：`context = dict(inputs)`，每节点执行后 `context.update(outputs)`（`workflow_runner.py:327`）。所有输出**平铺进一个 dict**。带来两类问题：
- **同名覆盖**：两个 LLM 节点都输出 `text`/`answer` → 后者覆盖前者（§6 实测已复现 `answer` 被错误覆盖）。
- **无类型/无来源**：变量下拉无法展示真实上游变量与类型，前端只能写死假列表（§3.3-1）。

### 4.3 无并行执行

熵舟 `_execute_workflow_graph` 为**单指针顺序拓扑**（`while i < len(exec_order)`）。Dify 1.17 引擎支持并行分支（graphon parallel）。当前对"扇出多条独立分支"场景无提速。

## 六、实测验证的 P0 正确性缺陷

> 以下结论来自对**运行中的熵舟后端**（`http://localhost:5000`）的直接在线实测，非静态推断。

### 6.1 条件分支（IF/ELSE）路由完全失效 —— **P0**

**测试方法**：构造 5 节点图 `start → if-else(判断 x==1，真则走 case 'true') → {Yes分支, No分支} → end`，输入 `x="1"`（条件为真，期望只执行 Yes）。分别用两种 `sourceHandle` 约定调用 `POST /api/workflows/<app_id>/run`，随后查询 `dify_workflow_node_executions` 与 `dify_workflow_runs`。

**实测结果**：

```
[A] sourceHandle=yes/no（前端画布实际产生的数据）
    实际执行节点：n_start, n_if, n_end, n_no, n_yes   ← Yes 与 No 两条分支都执行了！
    最终输出：    {"x":"1","__if_else_branch__":"true","answer":"no","text":"no"}
[B] sourceHandle=true/false（与 case id 对齐）
    实际执行节点：n_start, n_if, n_end, n_no, n_yes   ← 两条分支都执行了！
    最终输出：    {"x":"1","__if_else_branch__":"true","answer":"no","text":"no"}
```

**结论**：无论句柄如何命名，**IF/ELSE 的两条分支都被执行**，且由于扁平 context 的"同名覆盖"，最终输出 `answer` 被**非活跃分支（No）覆盖**（条件明明为真 `__if_else_branch__="true"`，输出却是 `"no"`）。**条件分流对下游节点不产生任何隔离效果**。

**根因（代码级定位）**：
1. `workflow_runner.py:230 _build_adjacency(active_branch)` 的分支过滤，在**初始拓扑构建时以 `active_branch=None` 调用**（`:274`），先得到包含**全部**节点的 `exec_order`；命中 if-else 后虽重算（`:330-343`），但"删掉不活跃边的目标节点"并**不会把它从已生成的 `exec_order` 里移除**，重算结果 `exec_order = list(executed_nodes) + new_order` 中，被过滤掉的分支节点因 `remaining_in_degree` 被错误清零而重新成为"入度 0 根节点"，于是**照样进入执行序列**。
2. **前后端句柄约定不一致**：前端 `WfNode.vue:24-27` 用 `id="yes"/"no"`，引擎期望 `case-{id}` 或 `id`（`'true'/'false'`）。全仓库无任何一处把 `yes→true` 映射（Grep 证实），即使修好第 1 点，句柄也对不上。
3. `IfElsePanel.vue` 的条件变量下拉是**硬编码假列表**，运行时 `if_else.py:64 _resolve_selector` 读的是 `condition.variable` 点号路径，二者语义脱节。

**影响面**：任何用到条件分支、问题分类（多路由）、迭代的工作流都会**逻辑错误/重复执行**，属最高优先级。

### 6.2 Chatflow 图执行被严重简化 —— **P1**

`workflow_runner.py:446 _execute_chat_graph`：对话类应用**只查找图中第一个 llm 节点并返回其文本**，不做任何图遍历/分支/多节点执行。意味着 Chatflow 的完整编排（条件、知识检索、多步）**实际未生效**，与 Dify 的 advanced-chat 差距极大。

### 6.3 Answer 节点变量替换方式脆弱 —— **P2**

`node_factory.py:160 _node_answer`、`nodes/llm.py:79` 用 `for k,v in context: answer.replace('{{'+k+'}}', v)` 做纯字符串替换：依赖 context 恰好有该 key、且不支持 `{{#node.var#}}` 的 Dify 标准语法、不支持嵌套对象字段。与 Dify 的 `Segment/变量选择器` 体系不兼容，DSL 迁移后**提示词里的变量大概率不生效**。

## 八、优化建议（按优先级 + 落地路线）

### P0（正确性，立即修复）

**8.0 重构分支执行模型（根治 §6.1）**
- 放弃"一次性静态拓扑 + 事后删边"的做法，改为 **Dify 式动态就绪调度**：维护 `in_degree` 与 `visited`，仅当某节点所有入边"来源被激活"才入队；if-else 命中分支后，**对未命中分支的下游做可达性剪枝**（从活跃节点集 BFS，未覆盖节点标记为 `skipped`，不执行）。
- 统一句柄约定：前端把 if-else 输出口 `id` 直接写成 **case id**（推荐 `sourceHandle = case.id`，如 `'true'/'false'` 或用分支 name/uuid），引擎 `expected_handle` 与之严格一致；增加 `yes↔true` 兼容层避免历史数据失效。
- 修复变量扁平覆盖：至少将每节点输出以其 `node_id` 命名空间写入（`context[node_id] = outputs`），并保留一份"最新值别名"做向后兼容；`_resolve_selector` 走 node 命名空间路径。
- **回归用例**：把 §6.1 的图固化成 `backend/tests/` 用例，断言"条件为真时 No 分支节点不被执行、`answer=='yes'`"。

### P1（核心编辑体验，尽快补齐，多数后端已就绪）

**8.1 变量引用选择器（投入产出比最高）**
- 新建 `components/workflow/inputs/VarReferencePicker.vue`：基于当前 graph 上游节点 + 各 `nodeRegistry`/后端输出定义，生成"节点→变量（带类型）"树；提供 `输入 '/' 唤出`、`{x}` 按钮两种入口。
- 在 `LLMPanel/IfElsePanel/HttpPanel/CodePanel/IterationPanel/KnowledgeRetrievalPanel` 全部替换纯文本框。
- 后端配套：`/api/workflows/<id>/available-vars`（按拓扑返回上游变量树）；`usePanelState.availableVariables` 改为真实数据。

**8.2 暴露"后端已支持、前端缺"的富字段**（零后端改动即可对齐 Dify）
- LLM 面板：context、vision、memory、结构化输出（JSON Schema）、失败重试、异常处理。
- 通用"节点设置"抽屉：retry_config + error_strategy（默认值/失败分支），落到 `data.retry_config`/`data.error_handle`，引擎已读取。

**8.3 画布交互补齐（编辑生产力）**
- 连线中点"+"插入节点：`WfCanvas` 增加自定义 edge 组件（`EdgeLabelRenderer` + 复用 `NodeLibrary` 作下拉）。
- 节点悬浮工具条：在 `WfNode.vue` 增加 添加/运行此节点/复制/删除/描述 按钮。
- 框选+多选+复制/粘贴/副本：接入 VueFlow `SelectionArea`、`onSelectionChange` + 剪贴板栈，补 `Mod+C/V/D`。
- 画布/节点/边 右键菜单（VueFlow context menu）。
- 运行态画布高亮：`RunPanel` 事件驱动更新节点 `data._status`（success/running/failed），`WfNode` 相应描边。
- 性能：`WfCanvas` 停止"每次 graph 变化全量重建 elements"，改为增量更新（用 VueFlow `addNodes/addEdges/updateNode`）；`elements` 用 `shallowRef`，node `data` 用 `markRaw` 包裹非响应式配置。

**8.4 引擎正确性/能力**
- `_execute_chat_graph` 改为真正的图遍历（复用 workflow 引擎 + answer 流式）。
- Answer/LLM 变量替换改用 Dify 标准 `{{#node.var#}}` 解析器（正则 + node 命名空间），与 DSL 对齐。
- 统一状态管理：删除或启用 `stores/workflow.ts`，消除三份并存状态（建议以 store 为单一事实源，画布受控于 store）。

### P2（体验对齐与生态）

- 草稿自动保存（复用 `PUT /graph`，前端 debounce + "自动保存 时间"提示）与发布前 diff 确认弹窗。
- IF/ELSE 支持多分支 ELIF + AND/OR + 类型感知操作符（对齐 Dify）。
- 代码节点接入真实编辑器（CodeMirror），移除 "json 伪语言"。
- 画布注释 Note（可缩放卡片）与评论 Comments（已有 `workflow_comments` 表，补前端）。
- 检查清单（发布前校验未配置必填项）、变量检查面板、整理节点快捷键 `Mod+O`。
- 迭代/循环的子画布容器化（容器内嵌套、iteration-start/loop-end 语义节点），当前用"子图识别"较易踩坑。
- 实时协作（可选，参考 `dify-1.17.1/web/.../collaboration`），依赖 WebSocket 独立服务（熵舟已有 `utils/ws.py`）。
- 并行分支执行（引擎就绪后）。
